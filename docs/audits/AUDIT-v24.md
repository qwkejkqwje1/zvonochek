# ZVONochek v24 — fallback генерации ключей P-256: кнопки оживают без generateKeyPair

Дата: 2026-10-30. База: v23 (проба окружения). GitHub не пушился, Cloudflare не деплоился.

## Диагноз окружения (подтверждён пробой v23 у владельца)

Проба v23 на машине владельца показала дословно:

> secure=true, subtle=object, generateKeyPair=undefined, sign=function,
> importKey=function, encrypt=function, UA: Mozilla/5.0 (Windows NT 10.0; …)

То есть контекст защищённый (https, secure=true), WebCrypto есть и почти
полон, но `crypto.subtle.generateKeyPair` **отсутствует**. Из-за этого
падали все четыре клиентских места генерации пары ECDSA P-256:

- `identity.js`: ensureDevice, ensurePersonal, ensureGuestDevice
  (а через них — личная ссылка и ключ устройства чата);
- `app.js`: гостевой эфемерный ключ исходящего дозвона без личной ссылки.

Звонки при этом работали и работают: звонковый путь обходится
importKey/deriveKey (deriveRoom), generateKeyPair ему не нужен.

## Что сделано: fallback в crypto.js

Отдельной секцией в конце `crypto.js` (не отдельным модулем — сознательно:
вся криптография проекта живёт в crypto.js, а новый файл потребовал бы
проводки через service worker и ?v= импорты):

- Константы кривой P-256 как BigInt (p, a=p−3, b, Gx, Gy, n — SEC 2 /
  FIPS 186-4).
- Аффинная арифметика точек: сложение/удвоение с одной модульной
  инверсией на операцию (расширенный алгоритм Евклида), скалярное
  умножение double-and-add. Для разовой генерации ключа это ~24 мс
  (замер в тесте) — fallback не на горячем пути.
- `p256PubFromPriv(dBytes)` — чистая часть: скаляр → координаты
  публичной точки (экспортирована для векторных тестов).
- `p256KeyPairFromPriv(dBytes, usages, algName)` — JWK пары →
  `subtle.importKey`. Семантика повторяет нативную пару точь-в-точь:
  usages разнесены по половинам (публичная: ECDSA `['verify']` / ECDH
  `[]`; приватная: `'sign'` либо `'deriveKey'/'deriveBits'` — importKey
  приватного JWK с `'verify'` WebCrypto отклоняет), публичный ключ
  экспортируем (identity.js достаёт raw), приватный — строго
  неэкспортируемый.
- `genP256KeyPair(usages, algName, forceFallback)` — публичный вход:
  **нативная generateKeyPair, если она есть (основной путь, поведение в
  нормальных браузерах не изменилось)**; fallback включается только при
  её отсутствии. Скаляр — `crypto.getRandomValues(32)` с rejection
  sampling в [1, n−1].

Все 4 клиентских вызова заменены на `genP256KeyPair()` (аргументы по
умолчанию = ECDSA sign/verify — семантика каждого места сохранена).
`worker/push.js` не тронут: это код Cloudflare Worker, не браузер,
generateKeyPair там есть.

## zvdiag.js

- Проба `__zvProbe`/`__zvEnvText` — без изменений, сводка по-прежнему
  дописывается к каждому баннеру.
- Загрузочная проверка изменена: фатальный баннер показывается только
  когда `crypto.subtle` отсутствует **полностью** (новый текст: «нет
  crypto.subtle»). Отсутствие одного generateKeyPair при живом subtle
  баннером не сопровождается — fallback это покрывает.

## Остаточный риск и границы

- Fallback исполняется **только** там, где нативной функции нет; в
  обычных браузерах код идёт прежним нативным путём — регрессия для них
  исключена конструкцией, а не надеждой.
- Математика fallback — самописная (BigInt-арифметика кривой), но
  проверена против OpenSSL на векторах и функционально против самого
  WebCrypto (importKey отверг бы битую точку/несоответствие JWK).
  Приватный скаляр живёт только в памяти на время генерации и внутри
  неэкспортируемого CryptoKey после импорта.
- Полевого подтверждения у владельца пока нет: следующий шаг — заливка
  v24 на GitHub Pages и нажатие тех же кнопок на той же машине. Если на
  этот раз упрётся во что-то другое, это назовёт баннер v22–v23.
