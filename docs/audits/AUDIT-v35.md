# AUDIT v35 — ntfy.sh как «слепой» резервный транспорт

Дата сборки: 31.10.2026. Решение владельца: «ntfy делаем».
База: дерево v34 (staged в repo34, дельта против GitHub main b47701a «32v»;
живой сайт на момент сборки — v32). v35 — единый релиз v34+v35 одним пушем.
Воркер НЕ трогали: /health останется v:32.

## Что сделано

### Конфиг (config.js)
- `CONFIG.NTFY_BASE = 'https://ntfy.sh'` — базовый адрес ntfy вынесен в
  конфиг: свой ntfy позже поднимается одной строкой, транспорты не
  переписываются. getWorkerBase/«Свой сервер» не тронуты.

### Сигналинг звонков (signaling.js) — пятый канал в гонке
- Топик: `zv1-` + sha256hex(топик комнаты) — по образцу MQTT-топика в
  chat-transport. Сам топик комнаты публичному серверу не показывается.
- Подписка: WebSocket `wss://ntfy.sh/<topic>/ws?since=<now-30с>`;
  принимаются только кадры `event === 'message'`, поле `message` — наш
  запечатанный конверт, уходит в существующий `_recv` (дедуп по mid,
  фильтры from/to/toInst — без изменений).
- Публикация: в веере `send()` после Nostr — POST на
  `https://ntfy.sh/<topic>`, тело = та же строка конверта байт-в-байт,
  что идёт в MQTT.
- Реконнект: экспоненциальный backoff 1.2с → 25с (как у Nostr), since
  пересчитывается на каждое подключение.
- Статус: в onStatus добавлены `ntfyUp/ntfyTotal`; app.js показывает
  ntfy в строке «Сигнал: …» и в логе входа в комнату.
- Голосовой мост (`_sendVoice`) через ntfy НЕ ходит сознательно:
  несколько чанков в секунду мгновенно упёрлись бы в троттлинг
  публичного сервера (см. ниже). Мост по-прежнему несут MQTT/Worker/Nostr.
- Пулы существующих реле и их реконнекты НЕ менялись (урок отката v34):
  изменения в signaling.js — только аддитивный канал и импорт sha256hex.

### Резервный транспорт чата (chat-transport.js, FallbackTransport)
- ntfy — третий канал рядом с MQTT (live) и Nostr (store), роль — live,
  как у MQTT. Хранимая лента (fetchSince) по-прежнему только Nostr.
- Топик: `zvchat1n-` + sha256hex(roomId) (тот же хэш, что у MQTT/Nostr;
  префикс отдельный, чтобы не пересекаться с `zvchat1/` и `zv1-`).
- Публикация: POST fetch, тело = blob байт-в-байт как в MQTT; результат
  учитывается в `send()` (`ntfySent`), ошибка/429 не роняет отправку,
  если сообщение унесли MQTT/Nostr.
- Подписка: WebSocket с тем же правилом since (см. ниже); реконнект 4 с.
- chat.js передаёт `ntfyBase: CONFIG.NTFY_BASE` в FallbackTransport.
  Порог включения fallback (8 с) и бейдж «Резервный канал» — без изменений.

## Защита от реплея кэша ntfy (ключевой риск публичного сервера)
Публичный ntfy.sh хранит сообщения топика 12 часов. Без защиты каждое
подключение получало бы весь кэш, включая вчерашние конверты. Закрыто
в три слоя:
1. **since при подписке.** URL подписки содержит `since = now − 30 с`
   (unix-время) — сервер отдаёт только свежее. Пересчитывается на
   каждое (пере)подключение, поэтому реконнект не тянет кэш. Окно уже,
   чем у существующей Nostr-подписки (60 с).
2. **Дедуп внутри сессии.** Сигналинг: существующий дедуп по `mid`
   конверта в `_recv` (повтор того же конверта игнорируется — покрыто
   тестом). Чат: дедуп по id сообщения ntfy в FallbackTransport
   (bounded Set, 2000 ключей) + существующий дедуп по хэшу blob на
   ingest в chat.js.
3. **Природа данных.** В кэше лежит только AES-256-GCM шифротекст;
   реплей старше окна since возможен лишь ручной перепубликацией
   захваченного конверта третьей стороной — тот же класс риска, что
   у давно работающих публичных MQTT/Nostr (там конверты тоже можно
   переотправить), нового доверия серверу не добавляется.

## Rate-limit публичного ntfy
Публичный ntfy.sh ограничивает частоту сообщений и подключений по IP
(при превышении — 429/отказ). Поведение v35 при троттлинге: деградация
только канала ntfy — POST глотает ошибку, подписка переподключается с
backoff; гонку в этот момент несут Worker/MQTT/Nostr. Канал изначально
спроектирован резервным (в чате — только при недоступном Worker дольше
8 с), поэтому троттлинг не может уронить ни звонок, ни чат.

## Остаточные риски
- Публичный ntfy.sh — чужая бесплатная инфраструктура: доступность и
  лимиты вне нашего контроля. Лечение заложено: NTFY_BASE в конфиге
  (свой ntfy) и резервная роль канала.
- Метаданные: оператор ntfy видит хэш-топик, тайминги и размеры
  шифротекстов — тот же профиль, что у публичных MQTT/Nostr.
- Полевая проверка не проводилась: живой прогон (звонок и чат при
  выключенном Worker, чтобы fallback дошёл до ntfy) — за владельцем
  после публикации.
