## A. Дозвон из чата + групповой звонок

Как устроено. В v27 intro участников не содержало данных личной
идентичности, поэтому в v28 добавлено отдельное подписанное управляющее
сообщение **`dial`** (в ленте не рендерится): `{masterPub, masterFp, cert,
chain}` устройства с личной идентичностью; публикуется один раз на комнату
(флаг `dialInfoSent`), гостевые устройства не публикуют ничего.

Ключевой нюанс протокола: адрес Inbox в штатном дозвоне выводится из
**секрета личной ссылки** вызываемого, а секрет — носитель доступа, в чат
его публиковать нельзя. Поэтому для чатового дозвонa app.js поднимает
**второй, аддитивный слушатель Inbox** на топике `chatdial-<sha256(masterPub)>`
(выводится из публичного ключа, секретов не раскрывает), а payload ring
запечатывается ECDH-ключом: эфемерная пара звонящего ↔ ECDH-ключ устройства
вызываемого (тот самый, что чат публикует для эпох), HKDF `zv-chat-dial-v1`.
Сервер входящих payload прочитать не может. Принятие такого звонка ведёт в
отдельную звонковую комнату из запечатанного `roomSecret` (аддитивная ветка
в обработчике «Принять»); обычный дозвон по личной ссылке payload без
`roomSecret` идёт прежним путём, бит-в-бит.

- Комната 1:1: кнопка «Позвонить» при наличии у собеседника masterPub делает
  настоящий дозвон (у него звенит рингтон как у обычного входящего), в чат
  падают приглашение с кнопкой входа и строка «📞 Дозвон: … — телефон
  звенит…»; исходы (принял/отклонил/не ответил) — системными строками по
  `onState`. Без masterPub — прежнее приглашение + честная пометка, что
  телефон не зазвонит.
- Группа: кнопка 📞 у каждого участника с masterPub в списке участников;
  «Групповой звонок» в шапке (видна при 2+ собеседниках): создаётся обычная
  звонковая комната `newSecret()` (групповой mesh — это та же комната на
  3+ участников, механизма group.js), приглашение — сообщением
  `system:'gcall:<secret>'` с кнопкой «Войти в групповой звонок», участникам
  с masterPub дополнительно уходит дозвон с тем же секретом комнаты;
  создатель входит сразу. Формат ring payload групповую ссылку позволил —
  ограничений не понадобилось.
- Стыковка — публичный хук app.js: `window.__zvDial = { ringPersonal(masterPub,
  link, {ecdhPub, name, callKind, onState}), openCallLink(link) }`. Логика
  Inbox в чате не дублируется.

Ограничения: дозвон возможен только участникам с личной идентичностью и
только пока их приложение живо (слушатель дозвонa из чата — live, без push:
пропущенные чат-звонки в журнал пропущенных не пишутся). Гость может только
получить приглашение в чат.

## B. Уведомления о сообщениях без VAPID (пока приложение живо)

- Открытая комната при скрытой вкладке/другом экране: тост в приложении
  (ник + превью, клик — в комнату) и, при выданном разрешении, системное
  уведомление `registration.showNotification` через SW; клик по нему шлёт
  странице `chat-notification` (seed в уведомление не кладётся).
- Неоткрытые комнаты: живого WS у них нет, поэтому раз в 30 с лёгкий
  `fetch?after=…` по сохранённым комнатам считает новые seq и поднимает тост
  со счётчиком, **не** помечая ничего прочитанным и не сохраняя (при входе
  всё подтянет обычный fetch).
- Приватность: настройка «Текст в уведомлениях» (список комнат на главном),
  по умолчанию **OFF** — тело уведомления «Новое сообщение». Звук (короткий
  WebAudio-beep) — настройка, по умолчанию **OFF**. Разрешение Notification
  запрашивается только по кнопке «Уведомления» в шапке списка комнат.
- Троттлинг: ToastGate — не чаще 1 тоста в 2 с на комнату, пропущенные
  считаются и добавляются «(+N)».

Ограничение: закрытое приложение уведомлений не получит — это сознательно
отложенный владельцем VAPID, серверный push в этой версии не тронут.

## D. Неубиваемость: резервные каналы чата

Новый модуль **`chat-transport.js`**: интерфейс транспорта
`{kind, send(blob), fetchSince(cursor), subscribe(cb), close()}`,
`WorkerTransport` — адаптер к существующим api()/WS chat.js (поведение
воркер-канала не менялось), `ChatTransportManager`, `FallbackTransport`.

Fallback — два подканала, наружу только тот же base64-шифротекст blob:
- **MQTT live**: те же публичные WSS-брокеры, что у звонков
  (`CONFIG.MQTT_BROKERS`), клиент — vendored `mqtt.min.js`. Топик
  `zvchat1/<sha256(roomId)>` (сам roomId брокеру не показываем), QoS 1.
  Только live-доставка онлайн-клиентам.
- **Nostr store**: голые WebSocket на первые 3 реле из `CONFIG.NOSTR_RELAYS`.
  Событие **kind 1** с тегами `['t','zvchat1']`, `['z', roomHash]`,
  `['s', ts]` и телом = blob. (kind 20001 ephemeral не хранится релеями;
  30000–39999 — replaceable/addressable семантика, поэтому взят обычный
  хранимый kind 1.) Подпись — vendored secp256k1 Schnorr (BIP340); ключ
  устройства — случайные 32 байта, созданные один раз и хранящиеся
  vault-зашифрованными в записи устройства (`identity.getChatNostrSecret`,
  как pinEnc в v26). Fetch: REQ `kinds:[1], '#t', '#z', since` + второй
  фильтр только по `'#t'` с клиентской фильтрацией по `z` (parse/verify
  проверяют подпись и тег комнаты). Дедуп — по хэшу blob и дополнительно по
  id сообщения при слиянии каналов.

Менеджер: основной канал — воркер. Живость: WS open/close + `/health` раз в
5 с с таймаутом 2,5 с; недоступность дольше **8 с** — переход в fallback,
бейдж «Резервный канал» в шапке. В fallback честно отключены: файлы и
голосовые (кнопки задизейблены с подписью), presence/typing (статусная
строка говорит «резервный канал»), receipts (галочка «ждёт основной
сервер»), коды приглашений и бэкап (ходят в воркер — при его недоступности
вернут ошибку, а не молчание). Сообщения fallback помечаются
`pendingWorkerSync` и хранят свой blob; при возврате воркера менеджер:
(1) публикует pending тем же blob (серверный дедуп по хэшу съедает дубли —
ресинк ровно один раз), (2) докачивает пропущенное, (3) снимает бейдж и
переподключает WS. Сортировка при слиянии — `(seq, если есть; иначе
ts+hash)`: сообщения не теряются и не двоятся (покрыто тестами слияния).
Воркер для пункта не менялся.

Честные ограничения: публичные брокеры/релеи видят сам факт активности
комнаты по её хэшу и шифротекст (как и воркер), MQTT без истории — офлайн-
участник получит fallback-сообщения из Nostr-ленты при следующем открытии
(релеи хранят kind 1 по своим правилам, гарантии срока нет); скорость и
доступность публичных реле — вне нашего контроля, это аварийный канал, а
не второй дом.

## E. Безопасность входа — видимость вместо вайт-листа

- **Ник обязателен**: до ввода ника лента и поле ввода в комнате скрыты,
  сообщения не рендерятся — при переходе по ссылке, создании и входе из
  списка комнат одинаково. Раньше вошедший без ника молча читал чат.
- **Реестр устройств** `seenDevices {dev, firstSeen, lastSeen, hasIntro}` в
  записи комнаты; источники — presence воркера, авторы сообщений, список
  online. В списке участников устройство без intro показывается строкой
  «Без ника · устройство …<последние 6 hex devPub>» с точкой онлайна.
- **Алерт о новом устройстве**: при первом появлении — локальная системная
  строка «⚠ К комнате подключилось новое устройство (…xxxxxx)» в ленту
  (+тост, если комната не перед глазами), один раз на устройство;
  историческая подгрузка при открытии комнаты алертов не поднимает.

Честно: это **видимость, а не контроль доступа**. Имеющий seed может читать
молча модифицированным клиентом — штатный клиент ему в этом больше не
помогает, но протокол не запрещает. Реальные контрмеры — PIN комнаты
(фаза 2 v26), отзыв короткой ссылки и смена эпохи (фаза 3 v26).

## F. Дизайн чата «как у Telegram» (структурно, палитра Soft Neon)

Только `#chatroom` и список комнат; главная и звонки не тронуты.
- Мета (время + галочки) — внутри пузыря справа снизу; статусы галочками:
  ✓ отправлено, ✓✓ доставлено, ✓✓ акцентным цветом прочитано; текстовые
  подписи убраны, расшифровка — в title. Состояние считается чистой
  функцией `receiptState` (покрыта тестами).
- Группировка подряд идущих сообщений автора (пауза < 5 мин): аватар только
  у нижнего в группе (слот сохраняется прозрачным), ник — только у первого,
  радиусы внутри группы меньше, хвост — у крайнего пузыря группы.
- Чипы дат по центру («Сегодня», «Вчера», дата); системные события —
  центрированные плашки-чипы (включая ⚠-предупреждения отдельным цветом).
- Шапка: аватар комнаты + название + статусная строка (онлайн/печатает/
  участники/резервный канал) в одной колонке.
- Поле ввода — круглая «пилюля»: скрепка внутри слева, микрофон/отправка —
  круглые справа. Фон ленты — тёмный с едва заметным паттерном из
  CSS-градиентов, без картинок. Меню сообщения — всплывающая плашка у
  пузыря (радиус + тень), поведение не менялось.
- CSS: +148 строк, только добавления/переопределения в существующих
  переменных палитры.

## G. «Свой сервер за 2 минуты»

- Корневой `wrangler.toml` **проверен против `worker/wrangler.toml`**: состав
  идентичен (main с поправкой на путь, биндинги ROOMS/INBOX/CHAT_ROOMS/
  PAIRING, миграции v1–v4, ALLOWED_ORIGINS) — менять было нечего, 0 строк.
- `SETUP-SERVER.md` + секция в README: кнопка **Deploy to Cloudflare**,
  пошагово по-русски: нажал → вошёл → Deploy → адрес
  `https://zvonochek.<аккаунт>.workers.dev` → Настройки → «Свой сервер».
  Честно написано: сайт (клиент) общий с GitHub Pages, данные идут в свой
  воркер; VAPID — необязательный отдельный шаг для push при закрытом
  приложении; форку сайта нужно поправить ALLOWED_ORIGINS.
- Настройка в приложении: Настройки → «5. Свой сервер» (localStorage
  `zvWorkerUrl`), единый резолвер **`getWorkerBase()` в config.js** —
  через него теперь ходят все модули: чат (все эндпоинты), Inbox/дозвон,
  pairing/бэкап, выдача TURN и Worker-сигналинг звонков (app.js передаёт
  адрес в Signaling как раньше, но из резолвера). Валидация: только https,
  без query/hash/кредов и без пути к конкретному эндпоинту; базовый
  подпуть допустим. Кнопка «Сбросить на сервер по умолчанию»; слушатель
  входящих при смене перезапускается сразу, идущий звонок сервер не меняет.
- Честно: **смена сервера данные не переносит** — комнаты/бэкапы живут на
  старом; личные ссылки и seed-ы те же, комнаты на новом сервере пусты до
  новых сообщений.
