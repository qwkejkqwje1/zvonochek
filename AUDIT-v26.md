## A. Фаза 2 — вход «ссылка + PIN» (техплан §5)

- `crypto.js: derivePinIkm(pin, seedBytes)` — PBKDF2-HMAC-SHA256,
  **600 000 итераций**, соль = `'ZVONochek/chat/pin/v1' ‖ Room_ID-кандидат`
  из seed-only вывода — точно по техплану. `pinIkm` подмешивается в IKM
  `deriveChatKeys` (механизм заложен ещё в v21): **без PIN не выводятся ни
  Room_ID, ни ключ, ни токен** — сервер PIN-комнату без PIN «не знает».
- Создатель: чекбокс «Защитить новый чат PIN-кодом» + поле PIN на главном
  экране. Минимум 4 символа; чисто цифровой PIN короче 6 знаков — с
  предупреждением (честная рамка техплана: цифры — это 13–20 бит, защита
  держится на медленном KDF и устности канала передачи).
- Ссылка PIN-комнаты получает маркер `&p=1` (PIN в ссылке НЕТ). Парсер
  обратно совместим: старые `#chat=` ссылки открываются как 1.1.
- Гость по PIN-ссылке: если PIN не сохранён локально — экран запроса PIN
  на главном экране; комната до ввода PIN не открывается и на сервере не
  создаётся. На своём устройстве PIN хранится только зашифрованным
  vault-ключом (`rec.pinEnc`), как seed.
- **Контрольная фраза**: 4 слова из ключа комнаты — в списке участников
  (шапка комнаты). Разный PIN → другая комната и другая фраза: ошибка ввода
  ловится устной сверкой. При первом входе по PIN в пустую комнату клиент
  подсказывает проверить PIN и сверить фразу — без пугающих «неверный PIN»
  (подтверждать существование комнаты нельзя).
- ⚠️ Отступление от техплана (слова): техплан предлагал список из 2048 слов
  × 3 слова (33 бита отпечатка). Реализован фиксированный список из
  **256 слов × 4 слова = 32 бита** (`CHAT_WORDS` в crypto.js): сопоставимая
  энтропия без внешней зависимости на 2048 слов. Отступление осознанное,
  на безопасность PIN не влияет (фраза — только сверка, не секрет).
- Не реализовано из §5: per-IP rate-limit на `/chat/` в воркере (кандидат
  техплана) — онлайн-подбор PIN по-прежнему упирается в то, что Room_ID
  вычисляется, а не «пытается»: атакующему нужен офлайн-перебор PBKDF2 600k
  по утёкшему хэшу токена; серверного оракула «PIN верен/неверен» нет.

## B. Фаза 3 — настоящая «Сменить эпоху» (техплан §6)

Заглушка заменена рабочей ротацией:

- У каждого устройства теперь **две пары ключей**: ECDSA (подписи, как
  раньше) и отдельная ECDH-пара (`identity.js: getChatDeviceEcdh`,
  генерация через `genP256KeyPair` — работает и в fallback-окружении
  владельца). Публичная ECDH-половина публикуется подписанным служебным
  сообщением `type:'ecdh'`; закрепляется у участников только при валидной
  подписи.
- Диалог «Сменить эпоху»: участники (никнейм, отпечаток devPub), чекбоксы
  «оставить»; себя снять нельзя. Новый секрет эпохи — **случайные 256 бит**
  (не вывод из seed — по техплану). Завёртка каждому оставленному:
  эфемерный ECDH → HKDF → AES-256-GCM; сообщение `type:'epoch'` (шифруется
  ключом уходящей эпохи) несёт завёртки по devPub. Системная строка в ленте:
  «Эпоха сменена · N».
- Ключ эпохи: HKDF(seed ‖ pinIkm ‖ epochSecret), метка
  `chat/v1/room-key/e<N>`. Room_ID и access-token при ротации НЕ меняются.
  Участники хранят секреты всех своих эпох (`rec.epochs[]`), сообщения несут
  поле `epoch` внутри шифротекста; расшифровка пробует ключи всех известных
  эпох.
- ⚠️ Отступления и честные ограничения:
  - В IKM ключа эпохи добавлен `pinIkm` (техплан писал HKDF(seed ‖
    epochSecret)): иначе PIN-комната после первой ротации теряла бы
    PIN-защиту ключей. Для комнат без PIN формула совпадает с техпланом.
  - Обёртка — AES-GCM, не AES-KW (техплан допускал оба варианта).
  - Серверная чистка сообщений старых эпох по команде инициатора (§6) НЕ
    сделана: это новый эндпоинт ChatRoom, а объём v26 сознательно ограничен
    клиентской криптой + алиасом в воркере. Старые шифротексты живут по
    обычному retention (ack+7д / 30д).
  - **Исключённый участник сохраняет старую историю** на своём устройстве и
    свой ключ эпохи 0 — прошлое ротация не лечит (свойство дизайна §7).
  - Исключённый сохраняет и access-token (выводится из seed): он не может
    ЧИТАТЬ новые сообщения, но технически может продолжать слать blob
    старым ключом, и клиенты их расшифруют как сообщения старой эпохи.
    Полное исключение = новая комната; зафиксировано честно.
  - Участник **без ecdhPub** (клиент v25 или не заходил с v26) завёртку
    получить НЕ может: в диалоге его чекбокс заблокирован с пометкой «нет
    ключа обмена — при смене эпохи не сможет читать новые сообщения».
    Догоняющей выдачи эпохи в протоколе нет и в UI не обещается: такой
    участник при ротации фактически исключается.

## C. Постоянная короткая ссылка (#join=)

- Код — 9 символов base64url (~54 бита), ссылка `#join=<код>`. Блок
  «Короткая ссылка» в комнате: ссылка, Копировать, Перевыпустить
  (revoke+create), Отключить. Создание — автоматически при первом открытии
  блока.
- Сервер: PairingDO расширен режимом алиаса (тот же DO, новых биндингов
  нет): `POST /pair/alias {codeHash, blob, adminHash}` (409, если занят),
  claim для алиаса — НЕ одноразовый и без TTL, **rate-limit 30 выдач/час**
  на codeHash (дальше 429), `POST /pair/revoke {codeHash, admin}` — сверка
  SHA-256(admin) с adminHash (неверный → 403). admin — случайные 128 бит,
  на устройстве хранится только в `rec.alias.adminEnc` (vault).
- Blob {seed, roomId} зашифрован AES-GCM ключом PBKDF2-HMAC-SHA256(код,
  соль `'zv-alias-v1'`, 200 000) — по образцу кода приветствия v25, но
  пространство отдельное: greet-код алиас не открывает и наоборот (другие
  соль и codeHash).
- Поле ввода на главном экране для 9-символьного кода пробует **сначала
  алиас, при 404 — код приветствия** (claim алиаса ничего не сжигает, а
  greet одноразовый — поэтому порядок именно такой).
- Честная рамка: короткая ссылка слабее длинной (≈54 бита против 256).
  Компенсации: медленный KDF, rate-limit выдач, отзываемость/перевыпуск в
  один тап, комбинация с PIN (фаза 2). Длинная ссылка остаётся главным
  ключом; короткую можно отключить, не трогая комнату.

## D. Автозагрузка картинок

- Файловое сообщение с mime `image/*` и размером ≤ 3 МБ: чанки скачиваются
  и расшифровываются автоматически при рендере, прогресс — тонкой полосой
  в карточке, затем превью в пузыре (как после ручного скачивания в v25).
- Больше 3 МБ или не картинка — карточка v25 (кнопка «Скачать»); ошибка
  автозагрузки → карточка с кнопкой «Повторить».

## E. Голосовые сообщения

- Панель ввода: при пустом поле кнопка отправки сменяется кнопкой
  микрофона (`#i-mic` уже был в спрайте). Запись: `getUserMedia({audio})` →
  MediaRecorder, mime по цепочке `audio/webm;codecs=opus` → `audio/webm` →
  `audio/ogg;codecs=opus` → `audio/mp4` → дефолт браузера. Панель записи:
  красная точка, таймер мм:сс, Отмена/Отправить; лимит 10 минут — автостоп
  с отправкой. Ошибка доступа к микрофону — понятный тост.
- Отправка — существующим зашифрованным файловым каналом v25 (чанки,
  отдельный файловый ключ); сообщение `type:'voice'`, мета несёт `durSec`.
- Рендер: пузырь-плеер — play/pause, полоса прогресса (клик — перемотка),
  длительность. Звук автоподгружается всегда (голосовые маленькие),
  object-URL и Audio-элемент кэшируются на сессию (fileState/voiceAudio).
