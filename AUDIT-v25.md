# ZVONochek v25 — мессенджерный слой чата: онлайн, «прочитано», файлы, код приветствия

Дата: 2026-10-30. База: v24 (fallback генерации ключей). GitHub НЕ пушился,
Cloudflare НЕ деплоился — сборка локальная, в `~/workspace/zvonochek-work/repo`.

Контекст: чат фазы 1 (v21–v24) заработал вживую у владельца с собеседником —
сообщения ходят, статус «На связи», приглашение на звонок из чата работает.
Владелец потребовал следующий шаг: уровень мессенджера «как в Telegram» по
функциям и ощущению, плюс простой способ быстрого подключения (была только
длинная ссылка с 43-символьным seed).

## Что сделано

### 1. Онлайн-присутствие
- `ChatRoomDO` (worker/chat-room.js): при WS-auth соединение регистрируется
  на устройство (attachment `{authed, device}` — как было); при подключении
  рассылается `{type:'presence', dev, online:true, ts}`, при отключении
  последнего сокета устройства — `online:false`.
- Hibernation: состояние НЕ хранится в памяти DO — список онлайн каждый раз
  пересчитывается из `state.getWebSockets()` + `deserializeAttachment()`,
  поэтому переживает гибернацию. Тот же список отдаётся в WS `ready` и в
  `GET /state`.
- Клиент: строка присутствия в шапке («N участника · M онлайн», либо
  «<ник> печатает…»), по нажатию на шапку — раскрывающийся список участников:
  аватарка, ник, зелёная точка онлайн / «был(а) в HH:MM» (lastSeen пишется в
  локальный реестр `rec.members[dev].lastSeen`).

### 2. «Прочитано»
- `/ack` расширен телом `{seqs, dev, read}` — обратно совместимо: клиент v21
  без `dev` работает как раньше.
- DO: новая таблица `members_state(dev PK, delivered_seq, read_seq, updated)`;
  значения монотонно растут (max). Любой ack поднимает delivered, `read:true` —
  ещё и read; остальным по WS уходит `{type:'receipt', dev, delivered, read}`.
- Клиент: доставку подтверждает каждое принятое сообщение (ack с dev);
  прочтение — пакетно по `lastSeq`, только когда чат реально на экране
  (открытая комната + видимая вкладка): при открытии, при докачке и при
  `visibilitychange → visible`.
- `GET /state` отдаёт сводку members_state + online для синхронизации при
  открытии комнаты.
- Рендер под своими сообщениями: «Отправлено» → «Доставлено» (delivered
  любого другого участника ≥ seq) → «Прочитано» (read всех остальных
  известных участников ≥ seq).

### 3. «Печатает…»
- Клиент при вводе шлёт по WS `{type:'typing'}` не чаще раза в 3 с; DO
  ретранслирует остальным без хранения; получатель показывает
  «<ник> печатает…» (или «Участник печатает…») в строке присутствия на 4 с.

### 4. Файлы (зашифрованные, через тот же DO)
- Клиент: кнопка-скрепка (новый SVG-символ `#i-clip` в спрайте) + скрытый
  `input[type=file]`. Лимит файла — 10 МБ. Нарезка по 256 КиБ открытого
  текста; отдельный файловый ключ (случайные 32 байта); nonce чанка —
  детерминированно: 4 байта случайной соли файла || 8 байт big-endian
  индекса (пара ключ+nonce уникальна: ключ одноразовый на файл).
- Чанки: `POST /chat/<room>/file {fileId, idx, total, blob}` с тем же
  access-token; метаданные — обычным сообщением `type:'file'`, text = JSON
  `{fileId, name, size, mime, chunks, salt, fileKey}` — оно шифруется ключом
  комнаты штатно, файловый ключ сервер не видит.
- DO: таблица `file_chunks(file_id, idx, blob, ts, PK(file_id, idx))`;
  лимиты: blob ≤ 512 КБ base64, total ≤ 40, idx < total, отдельный
  rate-limit 600/мин на комнату; `GET /file?fileId=&idx=` отдаёт чанк;
  retention alarm удаляет чанки старше 30 дней вместе с сообщениями.
- Получатель: карточка файла (имя, размер, кнопка «Скачать», прогресс на
  карточке); изображения после скачивания показываются превью прямо в
  ленте; ошибка чанка пишется на карточку.

### 5. Быстрое подключение — код приветствия (техплан v21 §6)
- Кнопка «Пригласить» в шапке комнаты: код из 9 символов base64url
  (≈54 бита), диалог — крупный код, короткая ссылка
  `<origin><path>#greet=<код>`, QR-код (существующий `vendor/qrcode.js`,
  тот же API, что использует app.js), подпись «код одноразовый, действует
  15 минут».
- Механика: K = PBKDF2-HMAC-SHA256(код, соль='zv-greet-v1', 200 000) →
  AES-GCM шифрует `{seed, roomId}`. Хранение — новый Durable Object
  `Pairing` (worker/pairing.js, биндинг `PAIRING`, миграция v4 в обоих
  wrangler.toml), адресуется `idFromName(codeHash)`, где
  codeHash = SHA-256('zv-greet-v1'||код). `POST /pair/create`,
  `POST /pair/claim` в worker.js; `/health` дополнен `pair:true`, версия
  воркера поднята до 25 синхронно с клиентом.
- Одноразовость: после успешной выдачи пара удаляется; лимит — суммарно
  не более 5 попыток claim (счётчик в meta; при маршрутизации по codeHash
  «чужие» попытки уходят в пустой DO и получают 404, не трогая пару);
  истёкшая пара → 410 и удаление; TTL при создании жёстко ограничен
  15 минутами (+30 с допуска на часы).
- **Решение по соли (зафиксировано по заданию):** соль PBKDF2 —
  фиксированная строка `'zv-greet-v1'`, а НЕ roomId: гость roomId не знает,
  он и есть полезная нагрузка blob. Защита пары: 54 бита энтропии кода +
  PBKDF2 200k (офлайн-перебор украденного blob дорог) + TTL 15 мин +
  одноразовость + лимит попыток. Серверный дамп пары бесполезен после
  истечения срока.
- Гость: поле ввода на главном экране принимает код из 9 символов и ссылку
  `#greet=` (формат определяется по длине: 43 — seed, 9 — greet-код);
  после claim комната открывается обычным `openRoomBySeed`.

### 6. Экран чата — «мессенджерный» вид
Только внутри `#chatroom` и списка комнат, в существующей палитре Soft Neon
и CSS-переменных; главная страница и звонковый UI не тронуты.
- Шапка: назад, название + строка присутствия (клик — список участников),
  статус соединения; ряд кнопок: Пригласить, Позвонить, Ссылка, Сменить эпоху.
- Лента: аватарки-кружки с инициалом (цвет из хэша devPub), пузыри с
  «хвостом» через радиусы, ник над чужими сообщениями, время и статус
  прочтения внутри/под пузырём, системные строки по центру, карточки файлов.
- Ввод: липкая нижняя панель — скрепка, поле, отправка; прогресс отправки
  файла — полоска над панелью.
- Список комнат на главной: превью последнего сообщения + время, счётчик
  непрочитанных (локально: чужие сообщения с seq > lastReadSeq), сортировка
  по последнему сообщению.

Сохранено поведение фазы 1: никнейм-флоу, подписи сообщений и TOFU-реестр,
дедуп по хэшу blob, докачка пропущенного, заглушка «Сменить эпоху».

## Компромиссы (честно)

- **Метаданные присутствия видны серверу**: факт WS-подключений устройств
  сервер знал и в v21; v25 добавляет явные presence-события и таблицу
  members_state — сервер видит, кто онлайн и до какого seq дочитал каждый
  участник. Содержимое по-прежнему не видит.
- **Размер файлов виден серверу**: в отличие от текста (паддинг до 4096),
  чанки файлов идут без паддинга — сервер видит число чанков и размер
  каждого, т.е. размер файла с точностью до ~256 КиБ. Имена и ключи файлов
  сервер не видит (внутри зашифрованных сообщений).
- Typing виден серверу как факт активности устройства (без содержимого).
